# Registration-interface repair: internal design review

The proposed repair is acceptable if it changes only the execution metadata
interface, with every original scientific choice and numerical operation
unchanged. This is a post-primary repair, not a new blind prospective study.
No actual arrays, study source or numerical routes were evaluated in this
review.

The original complete attempt is an execution failure. Its primary route
completed and reported a provisional single-route ledger classification; the
combined result is not accepted because the independent route stopped in its
registration guard before array decoding or study-source evaluation. Preserve
the original public registration, freeze receipt, complete first-attempt
outputs, logs and outer execution receipts. Earlier metric FAILs are unchanged.

The original guard expects `physical_diagnostic_evaluations_before_freeze`,
while the authenticated original registration records
`new_followup_physical_diagnostic_evaluations_before_freeze=0`. That is a real
machine-interface mismatch. A corrected guard must authenticate the exact
original registration bytes and interpret their strict integer zero as a
historical statement about the first public freeze. The repair registration
must separately record the known pre-repair physical route counts:
primary=1, independent=0. A generic zero-before-repair marker is false and
unacceptable. Missing keys, boolean/float counters, changed chronology pins
and inconsistent prior counts must be rejected.

Keep the original EXPERIMENT, protocol, source/interval/cutoff/control/precision
choices, target matching, tolerances, classification predicates, incoming data,
subtractions and numerical implementations unchanged. The only core change
may be the registration guard and its nonnumerical support. Compare the full
old/new core and its AST or exact remaining bytes to establish that distinction;
bind the original and repaired source hashes and retain metadata-only mutation
tests. Existing UNCOMPUTED text in copied original documents describes the
original preparation point; the repair README must explain the current state.

Publish and independently authenticate a separate repair registration before
any repaired execution. Rerun both complete routes and normal/optimized
validation under the original limits, then perform fresh standalone replay.
Do not reuse the first primary result as the repaired combined classification,
change scientific choices in response to it, suppress the original failed
attempt, or describe the amendment as made without prior outcomes. Exact-byte
GO for the repaired guard remains subject to inspection of its implementation,
chronology schema, invariance evidence and metadata-only tests.
