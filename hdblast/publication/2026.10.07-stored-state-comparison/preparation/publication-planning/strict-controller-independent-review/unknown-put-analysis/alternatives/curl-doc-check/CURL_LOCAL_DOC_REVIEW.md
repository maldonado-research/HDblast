# Installed curl documentation review

Scope: local CLI help/manual and installed libcurl header only. No network requests, credentials, controller imports or executions, repository/controller/state edits, or source implementation audit.

Installed curl and libcurl are 8.14.1, Debian security build 8.14.1-2+deb13u4, using OpenSSL 3.5.7. The executable supports HTTP/2 and HTTP/3. Exact version output and compiled-in full manual are retained alongside this report. Manual line numbers below refer to that captured manual.

The local documentation does not prove a strict one-wire-PUT guarantee from `--retry 0` or the proposed fresh-connection HTTP/1.1 flags.

## Documented request-repeat routes and controls

- Manual lines 4644–4650 describe `--retry` as the transient-transfer retry count. Zero is the default and disables that retry feature; the text lists timeout and HTTP 408/429/500/502/503/504. This is not a documented global prohibition on every subsequent HTTP request generated by other features.
- Manual lines 342–353 explicitly say `--anyauth` first does a request to inspect response headers and an upload “may require data to be sent twice”; the client must be able to rewind. Avoiding `--anyauth` and all challenge-based origin/proxy authentication, and sending an explicit bearer header without auth-negotiation options, removes the documented selected-negotiation route. The excerpt does not audit libcurl's implementation behavior for every unexpected auth response.
- Manual lines 2715–2747 say `--location` makes curl “redo the request” after a redirect; non-POST methods are retained, and `--request` overrides method selection. Lines 4551–4555 say its method string is used for all requests and can create unintended side effects with `--location`. Thus no redirect following is required for a single-URL PUT; `--retry 0` alone does not disable it.
- Manual lines 5353–5388 describe opt-in TLS 1.3 early data as not protected against replay. It says this option is used with GnuTLS, whereas this local executable uses OpenSSL. A no-early-data strategy removes this documented replay exposure; transport freshness itself is not a TLS replay guarantee.

## Fresh HTTP/1.1 strategy and its limits

- Manual lines 39–43: connection reuse is limited to URLs in one curl invocation and “cannot be performed between separate curl runs.” One URL in a fresh curl process, without redirects or negotiation, avoids previously cached libcurl connections. Merely specifying HTTP/1.1 or `Connection: close` is not the documented mechanism that forces initial connection freshness.
- Installed header `/usr/include/x86_64-linux-gnu/curl/curl.h`, lines 1392–1400: `CURLOPT_FRESH_CONNECT` explicitly selects a new connection for the upcoming transfer; `CURLOPT_FORBID_REUSE` forbids reuse of that connection **when done**. Neither header comment promises to suppress every internal resend/reconnect within one transfer. The CLI help has no direct flags with these two option names.
- Manual lines 2223–2238: `--http1.1` selects HTTP/1.1; HTTPS otherwise negotiates HTTP/2 by default. Explicit HTTP/1.1 avoids routes requiring HTTP/2 or HTTP/3, but these installed docs do not describe all HTTP/2 retry/fallback paths or establish their exact conditions.
- Manual lines 2049–2069: a custom header replaces the internal same-name header; an empty value after the colon removes an internal header. Thus `-H 'Expect:'` suppresses curl's Expect header. Lines 1467–1472 say `--expect100-timeout` controls waiting and then proceeds as if a response arrived; setting a timeout is not the documented way to suppress Expect. The local manual contains no 417-specific resend contract.
- Manual lines 3106–3115: `--no-keepalive` disables TCP keepalive messages; it is not a connection-pool reuse control.
- Manual lines 1130–1134: `-q`/`--disable` skips curlrc only when it is the first command-line parameter. This is needed to rule out unreviewed curlrc options. No credential/config files were read in this review.
- Manual lines 3168–3175: `--noproxy '*'` matches all hosts and effectively disables the proxy. Lines 3616–3618 also document an empty proxy string overriding proxy environment variables. This bounds the origin-connection strategy only when bypassing the proxy is compatible with the environment; it does not prove an upstream/server request has not already committed.

## Unresolved by local documentation

No implementation source or per-option libcurl man pages were found in the inspected standard installed documentation/source directories. The compiled-in CLI manual contains no explicit description of the often discussed stale-reused-connection resend, HTTP/2 REFUSED_STREAM/GOAWAY or HTTP_1_1_REQUIRED retry, or HTTP 417 resend behavior. Those claims require a matching patched-source review or tightly scoped local transfer tests; they cannot be accepted or excluded solely from this documentation check. Headers expose seek/read callbacks, but their comments do not enumerate all rewind/repeat triggers.

Even a source-verified single client send cannot turn a disconnect or incomplete response into evidence that a remote PUT had no effect. Ambiguous outcomes still require the controller's unknown-outcome latch and independent readback; transport flags alone cannot prove a server-side compare-and-swap publication guarantee.
