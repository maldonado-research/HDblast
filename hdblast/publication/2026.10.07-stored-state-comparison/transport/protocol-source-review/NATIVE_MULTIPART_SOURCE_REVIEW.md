# Native multipart upload source review

All observations are immutable GitHub GET-only source reads. No Zenodo POST, PUT, PATCH, DELETE, token display, or network mutator was executed. Deployment source/config parity is not independently established.

The current public Zenodo-RDM tree does **not** prove a usable multipart route for an owner token. Its legacy `/api/files/<bucket>/<key>` replacement declares only GET, PUT, and DELETE routes. Its PUT ignores multipart query parameters and deletes/reinitializes the target file before uploading the entire request stream. A fragment PUT to that route could therefore replace the intended ZIP with one fragment. An `uploads` link in a serialized legacy response is not proof of a callable multipart initialization route.

Immutable site source: [Zenodo-RDM legacy resource](https://github.com/zenodo/zenodo-rdm/blob/9370acc127c643aff4c43c59cf163c2982f3201c/site/zenodo_rdm/legacy/resources.py#L280), commit `9370acc127c643aff4c43c59cf163c2982f3201c`, dated 2026-10-06. The exact route declarations are lines 301–311; upload replacement is lines 237–277 and 336–352. The similarly named `MultipartUploadResource` class does not appear in the reviewed packages' resource sources.

The ordinary upstream `invenio-files-rest` API supports a different, older recipe, in `ObjectResource`: POST object URL with `?uploads=1` and JSON `{size: whole_size, partSize: chunk_size}`; zero-based PUT `?uploadId=<id>&partNumber=0..last`; completion **POST** `?uploadId=<id>` (not PATCH). This upstream protocol must not be assumed to survive the Zenodo legacy replacement. Source [views.py](https://github.com/inveniosoftware/invenio-files-rest/blob/140ef50fef4dea028d6ceb53cb51254eb5b6b355/invenio_files_rest/views.py#L750), commit `140ef50fef4dea028d6ceb53cb51254eb5b6b355`, SHA256 `8298615efb1fcd85b0fce107c02d01973fb9f806c219cf732e2bbc033044701b`. Defaults are 5 MiB minimum chunks, 5 GiB maximum chunks, and 10,000 parts. Final-part handling uses `size % partSize` and can expose an exact-divisibility edge case; avoid divisible sizes if this protocol is ever proven supported. Part Content-MD5 is parsed but not used by `Part.set_contents`; server-written checksum/ETag must be independently compared. Completion enqueues an async merge and may emit whitespace before JSON; a lost response needs GET reconciliation, not blind re-completion.

Current Zenodo's `uv.lock` pins `invenio-records-resources` 11.1.1 to `12ca933194d9f5c4ea15eacc72ec220ee2cec197`, and `invenio-rdm-records` 35.2.0 to `3903b289fb8181d30f63466c129cf79a4fb2d97b`. Those pinned packages contain a modern multipart provider. Its separate recipe is POST draft `/files` with an array containing `{key, size, checksum, transfer:{type:"M", parts, part_size}}`; response-generated one-based `/content/1..N` part URLs; PUT each returned URL; completion POST item `/commit`. The resource route and provider exist in dependency source. However, [Zenodo's permission override](https://github.com/zenodo/zenodo-rdm/blob/9370acc127c643aff4c43c59cf163c2982f3201c/site/zenodo_rdm/permissions.py#L115) admits ordinary users only for LOCAL type `L` on both set-content and commit; it omits upstream `M` permissions. Both content methods use the same `set_content_files` permission. Initializing an `M` file speculatively is therefore unjustified by reviewed site policy.

The exact sealed ZIP is 240,135,519 bytes, MD5 `e424502f12dbaacd36abaaabdd3fb74e`, SHA256 `ead5ffa3987c760d99da7a79189ff5ad766fb9bef6e032c489f4efb2316cd189`. An 8 MiB recipe would be 29 parts, final part 5,254,495 bytes, with every part below 10 MB. This arithmetic shows a size-compatible candidate; it does not establish a supported live upload route.

No native multipart mutator is approved by this source review. Reconcile the existing pending file with authenticated GET; investigate a full-file transport or prove live route availability without fragment PUTs. Keep the inventory/seal/source guards and all 29 fresh complete content stream requirements unchanged.
